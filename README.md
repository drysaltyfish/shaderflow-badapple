# Bad Apple → ShaderFlow WGSL

把一个**二值化视频**压进 ShaderFlow 的 `userfn` 里，逐像素无损、循环播放。
只需要一条命令，脚本会自动在 65536 字节预算内把分辨率/帧率/时长调到最优。

```bash
cd tools
uv add imageio-ffmpeg numpy           # 只需一次

# 全自动：自己找分辨率与帧率的最优组合
uv run python badapple.py

# 指定帧率（分辨率自动取该帧率下最大的）
uv run python badapple.py --fps 2.14

# 指定分辨率与时长（帧率自动取能装下的最高值）
uv run python badapple.py --size 64 --duration 60

# 指定分辨率与帧率
uv run python badapple.py --size 32 --fps 2.14 --out out/my.wgsl
```

默认输入 `tools/ardu_apple/data/source.mp4`（[justecorruptio/ardu_apple](https://github.com/justecorruptio/ardu_apple)
里的 Bad Apple 原片，480×360、30 fps、219.15 s）。输出是**可直接整段粘贴**
进 `http://<host>/player/` 编辑框的 WGSL。

## 1. ShaderFlow 的硬约束

来自 `web/shared/wall.js`（锁定模板 + `parseEditable`）：

```js
// 可编辑区被精确限定为「两个 const + 一个函数」，之后不允许任何内容
const positiveColor = <expr>;
const negativeColor = <expr>;
fn userfn(x: f32, y: f32, t: f32) -> f32 { ... }

// 锁定的片元着色器把它们映射成两条色带
let ret = clamp(userfn(uv.x, uv.y, t), -1.0, 1.0);
return vec4f(select(negativeColor * -ret, positiveColor * ret, ret > 0.0), 1.0);
```

| 约束 | 影响 |
|---|---|
| 可编辑区只有两个 const + `userfn` | **不能定义辅助函数、结构体、模块级数组**；数据与逻辑必须全塞进函数体 |
| 函数体禁止 `@group/@binding/@vertex/@fragment/@compute`、`fn fs/vs`、`struct Frame/VertexOut`、`frameData` | 不能声明管线资源 |
| `userfn` 返回 **f32 标量**，不是 vec4f | 画面只能落在「黑→positiveColor」与「黑→negativeColor」两条线上 |
| 提交源码 ≤ **65536 字节**（`MaxCodeBytes`） | 全部压缩预算 |
| `t = frameData.frame * 0.01`，两个页面都传 `floor(performance.now()/10)` | **t 就是页面加载后的秒数**，`u32(t*fps) % nf` 自动循环 |

**关键契合点**：二值视频只有两种颜色，而 f32 标量 + 两色色带**恰好也只能表达两种颜色**——
`ret = ±1` 即纯白/纯黑。上面那条「无法输出彩色」的限制在这里完全不构成损失。

## 2. 为什么不能直接用原项目的格式

原项目 `frames.h` 用的是「变化块位图 + 变化像素的 nibble RLE」，靠 Arduino
从头顺序扫描（`_get_nib(frame, ptr++)`）。

但 ShaderFlow 的 `userfn` 是 **fragment shader**：1080×1080 的格子上，
每个屏幕像素独立求值，只知道 `(x, y, t)`。为取 1 个像素去扫几千个 nibble
要付 10⁶ 次代价，不可行。

所以必须重新设计成随机访问格式——但**变长编码本身不一定要放弃**，
关键看「解码一个像素需要多少步」。见下一节。

## 3. 编码格式

```
每帧负载：
  [块变化位图]  NB 位，补齐到 u32                  NB = (S/BS)²
  [起始颜色]    1 个 nibble
  [run 流]      「属于变化块的像素」按图像行优先扫描序排列后的游程长度，
                变长 nibble 编码：
                  · <= 15        → 一个 nibble 直接是长度
                  · >  15        → 先写 0 转义，再写「3 位数据 + 1 位续」的
                                   分块链（小端），最后 +16

关键帧 = 位图全 1（负载结构与增量帧完全一致 → WGSL 里只有一条解码路径）
```

三条设计：

1. **关键帧与增量帧同构**：省掉一条分支；关键帧间隔 `key` 同时就是回退循环的确定上界。
2. **零字节复用帧**：整帧与上一帧完全相同时，索引直接指回上一帧负载，
   一字节都不花（解码端天然支持：位图全 0 就继续回退）。
3. **扫描序子序列**：run 流只覆盖「变化块」的像素——这是压缩率的来源。
   实测扫描序比块主序**少 22~28% 的游程**：

   | 分辨率/步长 | 扫描序 run/帧 | 块主序 run/帧 |
   |---|---|---|
   | 24×24 / 12 | 47.4 | 57.8（+22%） |
   | 32×32 / 12 | 66.7 | 84.0（+26%） |
   | 40×40 / 30 | 88.9 | 114.1（+28%） |

## 4. 随机访问怎么做到 O(1)~O(k)

解码像素 `(x,y)` 的第 `f` 帧：

```
1. 求所属块 b = (py/bs)*bn + (px/bs)
2. 从 f 往前回退，找最近一次把 b 标记为「变化」的帧 cf
   （关键帧全 1 → 循环上界 = key，确定终止）
3. 求 (x,y) 在「变化块像素扫描序子序列」里的下标 pos
4. 从 cf 的 run 流头部累加游程长度，直到覆盖 pos → 该像素颜色
```

第 3 步的 `pos` 有闭式解（同块的 16 个像素在扫描序里**不连续**，不能简单乘块号）：

```
pos = bs²·A + dy·bs·B + bs·C + dx
      A = 块行 < by 的脏块数      B = 块行 by 的脏块数      C = 该行里 bx 左边的脏块数

A、B：位图上的两段前缀 popcount（bmap 个 u32，2~8 次循环）
C   = rank(b) − A               // rank 本来就要算
```

**第 4 步是「全量遍历」**——不要求 O(1)。实测代价：

| 分辨率/步长 | run/帧 | 平均遍历步数/像素 |
|---|---|---|
| 24×24 / 12 | 47 | ~24 |
| 32×32 / 14 | 67 | ~34 |
| 40×40 / 30 | 89 | ~45 |

这个代价完全付得起，换来的收益见下节。

## 5. 体积账：二进制与文本两层

预算 65536 字节，而它是**源码文本**的字节数，所以有两层要压。

### 5.1 数据层（决定能装多少帧）

| 手法 | 收益 |
|---|---|
| 块变化位图 + 扫描序 RLE（vs 每脏块固定存原图） | **-14%（32×32）~ -38%（48×48）** |
| 零字节复用帧 | 视素材，静态段接近免费 |
| 关键帧间隔自适应 | 每帧增量比关键帧大时改存关键帧 |

### 5.2 文本层（同样数据写得更短）

u32 字面量的写法（`--help` 里有实现）：

```wgsl
var data = array<u32, 5511>(
0x3f2a1c,4095,20054016,0,...
);
```
```
① 十进制 / 十六进制取更短   → 0x0 写成 0 省 2 字符，从不更长
② 省掉 u 后缀               → array<u32,N> 会把 AbstractInt 隐式转成 u32
③ 逗号后不留空格、不缩进     → WGSL 不关心空白
④ 每行 8 个                  → 最长行 88 字符，不会折在数字中间
⑤ 注释改短、全 ASCII         → 中文注释 3 字节/字
```

字面量本身已到极限（平均 **8.88 字符**：u32 最多 10 位十进制，`0x` 前缀省不掉，
WGSL 也没有字符串字面量或 64 位整数可用）。能榨的是字面量之外：

| 组成 | 压缩前 | 压缩后 |
|---|---|---|
| data + index 字面量 | 61 252 | 58 723 |
| **数组缩进**（每行 4 空格） | 3 556 | **0** |
| 注释 | 806 | 136 |
| **合计** | **65 527** | **62 238（-5.0%）** |

效果：同一预算下从 464 帧 → **470 帧（完整覆盖 219.3 秒）**。

## 6. 可行域：分辨率 × 帧率 × 时长

信息量是常量，三者只能此消彼长。完整覆盖 219 秒时能选的档位
（`badapple.py` 自动搜索，单位：秒/帧率）：

| 存储分辨率 | 最高帧率 | 帧数 | 体积 |
|---|---|---|---|
| 16×16 | 5.00 fps | 1096 | 58.3 KB |
| 20×20 | 3.75 fps | 822 | 61.1 KB |
| 24×24 | 3.00 fps | 658 | 62.9 KB |
| 32×32 | 2.14 fps | 470 | 62.3 KB |
| 40×40 | 1.50 fps | 329 | 64.5 KB |
| 48×48 | 1.00 fps | 220 | 57.1 KB |

**帧率每降一半，时长大约翻倍**，所以「低帧率 + 高分辨率」几乎总比
「高帧率 + 低分辨率」划算；要长视频就只能牺牲分辨率。
整段 6572 帧 ÷ 22 万 bit ≈ **每帧 33 bit**，这是硬天花板。

另外两个可选补偿：

* `--filter smooth`（默认）：源像素中心之间做双线性插值 + `smoothstep(0.3,0.7)`。
  源图 32×32 铺到 1080px 是 **34 倍放大**，最近邻会是硬方块，插值后边缘平滑，
  观感上就是「分辨率变高了」。插值不占任何数据预算。
* `--dissolve-window 0.35`：在每帧**最后 35%** 的时间内与下一帧交叉淡化，
  其余 65% 单帧清晰。`1.0` 是全程双重曝光，**会明显发糊**，不建议。

## 7. 脚本用法

```
uv run python ardu_video/badapple.py [选项]
```

| 选项 | 说明 |
|---|---|
| `--video PATH` | 输入视频，默认 `../ardu_apple/data/source.mp4` |
| `--fps F` | 期望播放帧率（自动换算成抽帧步长） |
| `--size N` | 存储分辨率，须是 4 的倍数 |
| `--duration S` | 期望时长（秒） |
| `--min-fps F` | 未指定 `--size/--fps` 时可接受的最低帧率，默认 2.0 |
| `--out PATH` | 输出路径，默认 `out/badapple.wgsl` |
| `--start N` | 从源视频第 N 帧开始（默认 0） |
| `--thresh N` | 二值化阈值，默认 96 |
| `--key N` | 关键帧间隔，默认自动（16 或 32） |
| `--filter` | `smooth`（默认）/ `bilinear` / `nearest` |
| `--dissolve-window X` | 交叉淡化窗口，0 = 关闭 |
| `--budget N` | 源码字节上限，默认 65536 |
| `--master N` | 抽帧主分辨率，默认 128 |
| `--emit-full PATH` | 另存一份拼上锁定模板的完整着色器（给 naga 编译用） |
| `--no-verify` | 跳过逐像素回放自检 |

**自动调参规则**：约束（`--size/--fps/--duration`）优先满足；
自由维度上**分辨率优先**（从大到小试，第一个可行即最大分辨率），
**同分辨率下帧率优先**（步长从小到大试）。
最后按真实文本长度二分，把预算塞满。

控制台会逐阶段打印：视频信息 → 抽帧 → 二值化 → 每个候选组合的试算结果 →
选定参数 → 编码统计 → 源码体积 → 逐像素回放 → naga 编译。

## 8. 验证

脚本自带两道自检：

1. **逐像素回放**：内置独立解码器（照搬 WGSL 寻址）把生成的 editable 还原成
   帧序列，与源二值帧比对，**必须 0 差异**。这是无损性的硬证明——
   块增量只是「延迟引用上一帧」，RLE 只是编码形状，都不丢信息。
2. **naga 编译**：装了 `naga-cli` 就自动跑一遍完整着色器（顶点 + 片元）。

```bash
cargo install naga-cli                # 可选
naga out/badapple.full.wgsl out.spv   # 手动复核
```

浏览器端再加一层：整段粘贴进 `/player/` 编辑框后点「本地验证并提交候选」，
页面会用真实的 WebGPU 编译并渲染预览。管理员确认后才会上墙。

## 9. 被实测否掉的方案

留在这里避免重复踩坑：

| 方案 | 实测结果 |
|---|---|
| **像素主序 + 时间维 RLE**<br>（每个像素一条时间序列做游程） | 24×24/2.5fps：现状 25.9 KB，它 36.1 KB（熵下界 26.9 KB）。<br>每个 run 都要存长度，而平均 run 只有 3.4~7.6 帧——**存长度比信息本身还贵** |
| **块主序子序列** | 比扫描序多 22~28% 游程；只有实现简单这一个好处（`pos = rank*16 + local`） |
| **每脏块固定存 BS×BS 位**（`--coding block` 的原始形态） | 比 RLE 大 14~38%：块里只变 1 个像素也要写满 16 位 |
| **位图补齐到每块行一个 u32**（为了 O(1) 行 popcount） | 24×24 下位图从 2 字涨到 6 字（+128 bit/帧），吃掉的收益比省下的多 |
| **两层级块**（8×8 位图 + 4×4 子位图） | 估算只省 ~20%，而子位图数据的偏移需要前缀和，O(1) 随机访问失效 |
| **函数内 `const` 数组** | naga 能编，但 [slang 的 WGSL 后端](https://github.com/shader-slang/slang/blob/ab5db6cf5c645a816894db670dacd322ec59d3ac/docs/generated/tests/design/target-pipelines/wgsl/static-const-array-emits-var-private.slang)
会把它改写成 `var<private>`，历史上 WGSL 对「值类型的动态索引」有限制，故统一用 `var` |
| **纯 XOR 差分 + xz**（顺序解码上界参考） | 40×40/1fps：xz 15.2 KB vs 本格式 27.6 KB 数据。这点差距需要变长块内编码 + 前缀和，随机访问付不起 |
